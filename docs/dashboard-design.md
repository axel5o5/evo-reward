# Dashboard & Project Explorer Design
### `evo-reward` — Interactive visibility layer

*Design document for the project dashboard: a two-part system combining a static conceptual explorer (React) with a dynamic results dashboard and experiment launcher (Streamlit).*

---

## Why This Exists

The evo-reward project has extensive markdown documentation, but reading raw docs is painful and doesn't build intuition. The dashboard serves four audiences:

1. **You (the researcher):** Inspect results, launch experiments, monitor runs, compare conditions
2. **Your professor/reviewers:** Understand the methodology through interactive diagrams, not prose
3. **Teammates:** Navigate the codebase and understand module boundaries without reading all the source
4. **Future you:** Re-orient on the project after a break; everything is browsable in one place

---

## Architecture: Two Parts

### Part A — Static Conceptual Site (React + Vite + Tailwind + D3)

Interactive diagrams and reference material explaining *how things work*. Builds to static HTML/JS. No server dependency. Can be opened from a file or deployed anywhere.

**Technology choice:** React/Vite/Tailwind because the team already knows this stack. D3 for the data-driven diagrams (observation vector layout, force-directed module graph, mutation distribution plots). No backend needed — all data is extracted from the source code at build time via `extract_data.py`.

### Part B — Streamlit App (Python)

Results dashboard, experiment launcher, live monitoring. Reads directly from `results/` and `configs/`. Can shell out to launch experiments locally or via SSH.

**Technology choice:** Streamlit because it reads `.npz`/`.pkl` natively, uses matplotlib/plotly for exactly the chart types needed (KDE, time series with confidence bands, population dynamics), and requires zero JavaScript for the data-heavy parts.

## Part A: Static Site — Page Specifications

### 1. Observation Layout (`ObservationLayout.tsx`)

The most information-dense concept in the project. A horizontal stacked-bar visualization of the 205 dimensions:

```
[=== proximity (128) ===][== tactile (72) ==][v][a][w][e]
```

Each segment is color-coded and clickable. Clicking "proximity" expands to show:
- 32 sensors, each with 4 channels [prey, predator, food, wall]
- Winner-take-all logic explained with a small animation
- FOV: 120 degrees, range: 200 units
- How `max_s_prey` and `max_s_pred` are extracted for the reward equation

Data source: `obs-layout.json` extracted from `docs/interfaces.md` lines 162-188.

### 2. Reward Equation (`RewardEquation.tsx`)

Interactive version of the K&D reward equation:

```
r = w_eat * n_eaten + 0.01 * w_act * (||f|| / F) + 0.1 * w_prey * agg(s_prey) + 0.1 * w_pred * agg(s_pred)
```

Four sliders for `w_eat`, `w_act`, `w_prey`, `w_pred` (range [-10, 10]). Sample stimuli values adjustable (n_eaten = 0 or 1, motor_norm slider, predator proximity slider, prey proximity slider). The computed reward updates in real time.

Key insight this page communicates: negative `w_pred` + positive predator proximity = negative reward = fear = avoidance behavior. The user should be able to "feel" this by dragging sliders.

### 3. Agent Lifecycle (`AgentLifecycle.tsx`)

Flowchart showing one agent's life:

```
Birth (inherit genome, random policy, 40% parent energy)
  ↓
Observe → Act → Physics → Eat → Reward → Energy update
  ↓ (loop 1024 steps)
PPO Update (10 epochs, clipped surrogate)
  ↓ (loop until death or reproduction)
Death (energy < 0 or hazard h(t,e))  OR  Reproduce (prob b(e))
  ↓                                         ↓
Removed from world                    Child: mutated genome + fresh policy
```

The hazard and birth functions are rendered as interactive math: type in energy and age values, see the computed probability. Includes species-specific parameters (prey vs predator ζ values).

### 4. Evolution Visualizer (`EvolutionVisualizer.tsx`)

Three panels:
1. **Mutation distribution comparison:** Histogram overlay of Gaussian, Cauchy (t df=1), and Student's t(df=2). Highlights the heavy tail of t(df=2) — "why this matters: occasional large jumps explore reward space faster than Gaussian."
2. **Genome mutation animation:** A parent's 4 weights shown as bars. Click "mutate" to see noise added, clipping applied, and child genome produced. Repeat to build intuition for how the population drifts.
3. **Population drift:** Small animated scatter plot of 50 agents' `(w_prey, w_pred)` values over 100 simulated mutations. Shows how the population spreads and clusters.

### 5. Simulation Loop (`SimLoopDiagram.tsx`)

The 10-step per-tick loop as a vertical stepper:

```
Step 1: Get observations for all agents          [agents.py → get_observation()]
Step 2: Sample actions → write to rollout buffer  [policy.py → sample_action()]
Step 3: Step physics (phyjax2d)                   [environment.py → step_physics()]
Step 4: Check eating events                       [environment.py → check_eating()]
Step 5: Compute rewards → write to rollout        [agents.py → compute_reward()]
Step 6: Update energies                           [lifecycle.py → update_energies()]
Step 7: Process births and deaths                 [lifecycle.py → process_births_and_deaths()]
Step 8: Regenerate food                           [lifecycle.py → regenerate_food()]
Step 9: PPO update (if rollout buffer full)       [ppo.py → ppo_update()]
Step 10: Log metrics / save checkpoint            [metrics.py → log_step()]
```

Each step is expandable to show the function signature, key parameters, and data flow (what goes in, what comes out). Clicking the module name links to the source file.

### 6. Codebase Map (`CodebaseMap.tsx`)

Force-directed D3 graph of the 8 source modules. Nodes sized by line count. Edges derived from import analysis:

```
environment.py ← agents.py ← reward.py
environment.py ← lifecycle.py ← evolution.py
policy.py ← ppo.py
metrics.py (standalone)
run_experiment.py → (all modules)
```

Clicking a node shows its public API (function signatures). Clicking an edge shows the data contract (what types flow between modules).

### 7. Config Reference (`ConfigReference.tsx`)

Every parameter from `baseline_faithful.yaml` in a searchable, filterable table:

| Parameter | Value | Paper Source | Code Source | Notes |
|-----------|-------|-------------|-------------|-------|
| `prey_c_b` | 1.0e-4 | Table 2: 2.5e-6 (labels c_a/c_b swapped in paper) | `20251122-predator-square.toml:24` | **Paper Table 2 has labels swapped; magnitudes match code** |
| ... | ... | ... | ... | ... |

Grouped by category (World, Population, Sensors, Energy, etc.). Rows where code and paper disagree are highlighted. Filter to show only discrepancies.

### 8. Config Diff (`ConfigDiff.tsx`)

Side-by-side comparison of any two config YAML files. Highlights differences. Preset pairs:
- `baseline_faithful` vs `baseline_simplified` (shared policy change)
- `baseline_faithful` vs `axis1_mlp_reward` (MLP genome change)
- "Paper Table 2 values" vs "Code values" (the discrepancy analysis)

### 9. Deviation Tracker (`DeviationTracker.tsx`)

The D1-D10 entries from `emevo-diff.md` rendered as an interactive table with:
- Status: confirmed / resolved / struck-through
- Risk level: high / medium / low
- Component affected
- Expandable detail showing emevo source, our implementation, and justification

### 10. Docs Viewer (`DocsViewer.tsx`)

Renders all `docs/*.md` files with proper navigation sidebar and cross-linking. Clicking "[see emevo-diff.md]" navigates there. Uses `react-markdown` or `@mdx-js/react`. Not a replacement for the other pages — this is the fallback for docs that don't have their own interactive page.

### 11. Session Timeline (`SessionTimeline.tsx`)

Visual timeline built from git commit history. Each commit tagged with `[Phase X]` in the message is rendered as a milestone on a horizontal timeline. Shows:
- What was built (from commit message)
- Which files changed (from git diff stat)
- Test count at that point (from commit message or tag)

Data source: `git-timeline.json` generated by `extract_data.py` parsing `git log --format=...`.

## Part B: Streamlit App — Page Specifications

### Page 01: Run Overview

Single-run deep dive. Sidebar selects condition + seed by scanning `results/` for `metrics.npz` files.

**Plots:**
1. Reward weight trajectories (4 subplots: w_eat, w_act, w_prey, w_pred). Mean +/- std across population over time. Horizontal dashed line at y=0. Reproduces K&D Figure 7.
2. Population dynamics (2 subplots: prey count, predator count over time). Reproduces K&D Figure 6.
3. Reward weight KDE scatter (w_prey vs w_pred, colored by agent lifetime). Reproduces K&D Figure 8/12.
4. Energy distribution over time (violin or box plot per species per logged step).
5. Capture rate and food consumption rate over time.

**Data source:** `np.load("results/{condition}/seed_{seed}/metrics.npz")` with keys matching `MetricsLog` field names.

### Page 02: Comparison

Overlay plots from multiple seeds or conditions. Select runs via multiselect widget.

- Reward weight trajectories with one line per seed, same subplot
- Population dynamics overlaid
- Statistical summary: "w_pred < 0 in 3/5 seeds at step 10M: PASS"
- Table of Phase 1a success criteria with per-seed values

### Page 03: Experiment Matrix

Grid showing the factorial experimental design:

```
                      | Seed 0  | Seed 1  | Seed 2  | Seed 3  | Seed 4  |
baseline_faithful     | PASS    | running | -       | -       | -       |
baseline_simplified   | -       | -       | -       | -       | -       |
axis1_mlp_reward      | -       | -       | -       | -       | -       |
axis2_social_obs      | -       | -       | -       | -       | -       |
axis3_temporal_reward | -       | -       | -       | -       | -       |
axis4_lstm_policy     | -       | -       | -       | -       | -       |
```

Auto-populated by scanning `results/` and `configs/`. Clicking a cell opens the Run Overview page for that condition/seed. Color-coded: green=PASS, red=FAIL, yellow=running, gray=not started.

### Page 04: Hypothesis Tracker

The 7 hypotheses from `experimental-plan.md` as interactive cards:

```
H1: Reward convergence speed
  Prediction: Shared policy → faster convergence
  Tests: Phase 1a vs 1b comparison
  Status: UNTESTED
  Evidence: [none yet]

H5: Qualitative robustness
  Prediction: Fear + social affiliation emerge under ALL architecture combos
  Tests: All Phase 1 runs
  Status: UNTESTED
  Evidence: [none yet]
```

Status updates manually or from `validate_replication.py` output. Links to relevant comparison plots.

### Page 05: Agent Inspector

Individual agent lifecycle drill-down. Requires checkpoint data (`.pkl` files).

Select a checkpoint step. See all agents at that moment as a scatter plot (position colored by species). Click an agent to see:
- Reward genome weights
- Age, energy
- Parent ID (trace lineage)
- If multiple checkpoints: energy trajectory, reward weight inheritance chain

This is the most data-intensive page — loads full checkpoints on demand, not by default.

### Page 06: Paper Comparison

Side-by-side: K&D's published figures (embedded as images from `dashboard/site/public/paper-figures/`) next to your reproduced plots from the same run. The visual test of "did replication succeed?"

### Page 07: Config Editor

Load a YAML config. Edit parameters via form widgets:
- Sliders for continuous values (with min/max from config schema)
- Dropdowns for categorical values (`policy_mode`, `reward_type`, etc.)
- Text input for string values

**Validation:** Real-time warnings for:
- Values outside expected ranges (e.g., `mutation_scale > 10` — probably a typo)
- Missing required keys
- Type mismatches

**Presets:** "Start from baseline_faithful" → toggle one axis → auto-fill changes. Shows a diff against the base config.

**Save:** Write to a new YAML file in `configs/`.

### Page 08: Launcher

Two modes:

**Local:**
```python
subprocess.Popen([
    "python", "scripts/run_experiment.py",
    "--config", config_path,
    "--seed", str(seed),
    "--max-steps", str(max_steps),  # optional, for smoke tests
])
```

**Remote (SSH):**
Configured via `.env`:
```
REMOTE_HOST=user@gpu-machine.example.com
REMOTE_KEY_PATH=~/.ssh/id_rsa
REMOTE_PROJECT_PATH=/home/user/evo-reward
```

Flow: scp config to remote → ssh start in tmux → periodically scp back `metrics.npz` for monitoring.

PID tracking: write `.pid` file to `results/{condition}/seed_{seed}/` so the monitor page can check status.

### Page 09: Live Monitor

Polls `results/` for in-progress runs (detected by `.pid` file or recent `metrics.npz` modification). Shows:
- Current step / total steps (progress bar)
- Live population counts
- Current mean reward weights
- Estimated time remaining (from step rate)
- Last few log entries

Auto-refreshes every 30 seconds.

## Auto-Sync: Code Changes -> Dashboard

### Category 1: Results data (automatic)
The Streamlit app reads `results/` at runtime. New completed runs appear immediately.

### Category 2: Conceptual content (build step)
`extract_data.py` parses the source code and docs to generate the JSON data files consumed by the static site. It extracts:

- **obs-layout.json**: Parse the observation vector table from `docs/interfaces.md`
- **module-deps.json**: Parse `import` statements in `src/*.py`
- **config-schema.json**: Parse `configs/baseline_faithful.yaml` with comments as metadata
- **sim-loop-steps.json**: Parse the simulation loop from `docs/interfaces.md`
- **deviations.json**: Parse `docs/emevo-diff.md` D-entries
- **git-timeline.json**: Parse `git log --format='%H|%s|%ai|%an' --all`

**Integration with Vite:** A custom Vite plugin runs `extract_data.py` before dev server starts and before production build. So `npm run dev` always has fresh data.

```typescript
// vite.config.ts
import { execSync } from 'child_process';

export default defineConfig({
  plugins: [
    react(),
    {
      name: 'extract-data',
      buildStart() {
        execSync('python3 ../extract_data.py', { cwd: __dirname });
      }
    }
  ]
});
```

### Category 3: Structural changes (manual)
Adding a new source module or changing MetricsLog fields requires updating dashboard code. This is rare and flagged in session prompts when it happens.

## Same Repo Decision

The dashboard lives in the same repo as the simulation code. Reasons:

1. `extract_data.py` needs relative paths to `src/`, `docs/`, `configs/`
2. The Streamlit app imports from `src/` for config loading and data format consistency
3. Version coupling: dashboard and simulation must stay in sync
4. One `git log` shows everything — code changes and dashboard updates together
5. The dashboard is *about this specific project*, not a general tool

The `dashboard/` directory at project root keeps it cleanly separated. `.gitignore` handles `node_modules/` and build artifacts.

## Implementation Notes (2026-04-09)

- **Tailwind v3** used instead of v4 — the `@tailwindcss/vite` v4 plugin has native oxide binary issues on macOS. Using PostCSS-based v3 config instead.
- **React pages use lazy loading** via `React.lazy()` + `Suspense` for code splitting.
- **DocsViewer** requires a symlink `dashboard/site/public/docs -> ../../../docs` to load markdown at runtime.

## Potential Issues and Mitigations

### No results data yet
`synthetic_data.py` generates fake `metrics.npz` with plausible trajectories (w_pred drifting negative, Lotka-Volterra population oscillations, reasonable energy distributions). The dashboard can be fully developed and tested before any real experiment completes. A "synthetic data" badge appears on plots when using generated data.

### phyjax2d placeholder
Until Session 5 integrates phyjax2d, experiment launches will produce invalid physics. The launcher should warn if `step_physics` is still a placeholder (detected by checking for the NotImplementedError in the source).

### Large checkpoint files
With 150+ agents, each with Flax parameter trees, checkpoints are large. The results dashboard loads `metrics.npz` (small, aggregate data) by default. Full checkpoints are loaded on-demand only for the Agent Inspector page.

### Streamlit state management
Streamlit reruns the script on every interaction. The experiment launcher needs persistent process state. Use `st.session_state` for subprocess handles. For long-running experiments, write a `.pid` file that the monitor page checks independently.

### Stale extracted data
If `extract_data.py` hasn't been re-run after a source change, the static site shows outdated information. The Vite plugin mitigates this for dev/build, but a manual `python extract_data.py` is needed if only looking at the built site. Consider adding a "last extracted" timestamp to each JSON file and showing it in the site footer.
